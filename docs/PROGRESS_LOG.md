## Open items

### Blocking real (non-demo) use
- **Vaults #0-#3 can never release funds** (bound permanently to the old placeholder manager). Only campaigns published after 2026-09-19 use the real MilestoneManager.
- **The vault still emits no event on release;** the ledger learns about releases from `MilestoneManager.MilestoneReleased`. That is sound only while every vault is bound to a manager that emits it (true for all new vaults).
- **Users who registered with their own wallet cannot publish campaigns or donate,** because VERA cannot sign for an external address. Wallet connect / SIWE is not built and is not yet scheduled.

### Cost and operations
- **Gas spikes can drain the sponsor.** On 2026-09-19 Amoy's gas price briefly hit **570 gwei** (normally about 30) and deploying `MilestoneManager` with `forge create` cost **1.41 POL** for 2.5M gas, because no price cap was set. **Before any deploy, check `cast gas-price` and pass `--gas-price`/`--priority-gas-price`.** The app now refuses sponsored actions above 150 gwei (`gasPriceRefusal` in `lib/chain/sponsor.ts`) instead of paying it.
- **Publishing a campaign costs about 0.2 POL at 30-40 gwei, not 0.04:** the vault deploy is about 6M gas and the organizer is topped up with 1.5x the estimate. Escrow actions (define, attest, approve) are now funded from their own gas estimate plus 30%, not a flat allowance; the actor's leftover stays in their wallet.
- **Live test runs strand POL:** each run creates about nine throwaway wallets, and their leftover gas cannot be recovered (their keys lived in an in-memory database). Budget about 0.5 POL per run.
- **Gas is sponsored, so it costs POL.** Generated wallets start with none. The sponsor (`FACTORY_OWNER_KEY`, the deployer wallet, about 1.90 POL on 2026-09-19) tops them up first: about 0.04 POL to publish a campaign, about 0.03 POL for a donor's first donation and less afterwards (leftover POL stays in the donor's wallet). If the sponsor runs dry, the action fails with a clear message and can be retried after a top-up (see `mining_instructions.md`).
- **Features that need `FACTORY_OWNER_KEY` in `apps/web/.env.local`:** organizer on-chain sync, campaign publishing and donations. Without it the admin console says sync is not configured and the campaign page says donations are switched off. `FACTORY_ADDRESS` alone (needed by the indexer) is safe and leaves those features off.
- **There is no background worker** (a serverless host would not keep one alive). The indexer refreshes when someone reads a page that calls `syncIfStale`, so its lag is about 16 s (2 confirmation blocks plus the 10 s refresh window). If nobody visits, nothing updates until the next visitor.
- **The browser drives a donation** (`/advance` about every 1.5 s). If the donor closes the tab mid-way nothing is lost on-chain and no step repeats, but it stays PENDING until they reopen it from "Your donations".
- **The donor's receipt says "confirmed" a few seconds before the public ledger shows it** (measured 10.7 s); the receipt says so.
- **Reconciliation reads historical state** at the indexed block, which public RPCs only serve for recent blocks. If the indexer falls far behind, the check reports "could not read", never a false match.
- The `Secure` cookie flag is set in production mode, so testing `next start` over plain http works on localhost in most browsers but not Safari.

### Product decisions to revisit
- **An organizer can donate to their own campaign,** which can inflate its numbers. Wallets are free and everything is public on-chain, so blocking it would be cosmetic; left open on purpose. Decide before real use.
- **Sessions** are a single 24 h signed cookie (SPDD 13.2 asks for 15-minute access plus rotating refresh tokens). Login is custom (bcrypt + `jose`), not Auth.js. Duplicate signup reveals that an email exists.
- **Organizer KYB:** the first admin comes from the local `admin:promote` CLI; documents are stored as a browser-computed hash only (no upload); registration numbers are not checked for uniqueness; an organizer with an unverified own-wallet address can be approved on-chain for an address they may not control (harmless, but revisit with SIWE).
- **Milestone state:** the public dashboard now counts attestations, council approvals and releases from indexed chain events; the organizer and role consoles read the contract directly. The database `milestones.status` column is only a cache (RELEASED after a confirmed release) and is not used for display.
- **`CampaignVault.pause()`** is organizer-gated with a string revert; SPDD §18.2 specifies a compliance role.
- Generated wallet keys are AES-256-GCM encrypted with `WALLET_ENCRYPTION_KEY`; losing that key makes those wallets unrecoverable (testnet-only keys). The donation ledger shows wallet addresses (public on-chain anyway), never an email or name.

### 2026-09-21 - Step 13b: client-side beneficiary hashing
- `lib/beneficiary/clientHasher.ts`: `normalizeIdentityFragment` (Unicode NFKC, lower case, trimmed, inner whitespace collapsed) and `hashIdentityFragment(raw, programSalt)` returning `0x` plus 64 hex, i.e. a `bytes32` for the registry: SHA-256 of `salt + NUL + normalized fragment`. NFKC was chosen so the same Devanagari or accented name typed on different keyboards, and full-width digits, produce one fingerprint. It throws on an empty fragment or an empty salt instead of hashing nothing (every blank entry would otherwise collide as a duplicate). The NUL separator means no salt/fragment split can match another.
- `lib/hash.ts` (new): `sha256Hex`, `sha256HexOfFile`, `bytesToHex`, shared with the two forms that each carried a private copy. **The copies were not identical:** `AttestForm` used `0x` plus hex and `OrganizerApplyForm` bare hex (the server's schema requires bare 64-hex there). The helper returns bare hex and `AttestForm` adds its own `0x`, so neither call site's output changed. Placed in `lib/hash.ts`, not under `lib/beneficiary/` as the plan said, because it is not beneficiary-specific.
- **Tests:** 14 new (web 229), including the published SHA-256 vector for `abc`, an independent cross-check against Node's `createHash` (so the helper cannot agree only with itself), determinism, spelling-insensitivity, different salt gives a different hash, and that the raw text never appears in the hash. **Not re-checked in a browser:** the two forms' file pickers were only type-checked, linted and covered by the helper's tests.

### 2026-09-19 - Step 4: `MilestoneManager.sol` written and tested (not deployed)
- One shared manager for all vaults. It only works with vaults bound to it (`vault.milestoneManager() == this`).
- **Lifecycle:** the vault's organizer calls `defineMilestone(vault, targetPct, M)` (percentages total at most 100, M >= 2 so no single attestor can verify, NFR-10). Global attestors call `submitAttestation(vault, index, proofHash)`; each counts once and the organizer cannot attest. At M the milestone becomes Verified.
- **Release:** `release(vault, index)` is permissionless once all milestones total 100, they are released in order, and the milestone is Verified. Up to the auto-release limit only attestors are needed; above it `councilThreshold` (default 3, minimum 2) council approvals are also required. The limit is snapshotted per milestone when defined, so the owner cannot later skip the council.
- **Amount:** the milestone's cumulative percentage of everything the vault ever raised (balance plus released) minus what was already released, so late donations are shared fairly. Paid to the vault's organizer; nobody chooses the recipient.
- **Events:** `MilestoneDefined`, `MilestoneAttested`, `MilestoneVerified`, `CouncilApproved`, `MilestoneReleased(vault, index, recipient, amount)`. The last one is what the ledger must index, since the vault emits nothing.
- Tests: 21 new (below/at threshold, duplicate attestor, council needed above limit, ordering, late donations, role checks, paused vault, fuzz "never pays more than raised" at 10,000 runs). `forge test` 45/45.
- **Known limits to revisit:** (1) the Factory validates the 100% split but does not store milestone percentages, so an organizer could define a different split on-chain than in the app; (2) payouts go straight to the organizer, since Disbursement (SPDD §18.4) does not exist and the manager is immutable; (3) attestor and council lists are owner-curated, so the owner is trusted to pick honest people; (4) removing a council member does not undo approvals they already gave; (5) the SPDD's admin-expense cap is enforced in the Factory, not here.

### 2026-09-19 - Step 10: Donation flow / simulated on-ramp (FR-CMP-02)
- **Design (a resumable state machine, not one long request):** a donation is several transactions (gas, mint, optional fee, approve, deposit) that can take 15-40 s, too long for one serverless request. `POST /api/v1/donations` only records a PENDING donation; the browser then calls `POST /api/v1/donations/:id/advance` about every 1.5 s, and each call sends ONE step's transaction, **saves its hash before waiting**, and waits briefly for it to be mined. Any process can resume it. A lock (`locked_until`, atomic compare-and-set) stops two requests running the same step. `retry` resumes a FAILED donation from the step that failed, never repeating earlier steps.
- **The money rules (SPDD §8.9, FR-CMP-02):** a donation becomes CONFIRMED only after the deposit's receipt is read from the chain **and** its `DonationReceived` event (right vault, right donor, right amount) is verified. An error while merely *checking* a transaction that was already sent leaves the donation PENDING, never FAILED (found in my own review: it would otherwise report failure for a deposit that may have gone through). The mint is exactly the donation (+ fee) and the approval is exactly the donation, so a duplicate deposit could not go through even by accident.
- **Every transaction comes from the donor's own wallet:** the server decrypts the donor's generated-wallet key and signs as them, so on-chain the donation truly comes from the donor; the platform only sponsors gas. `lib/chain/sponsor.ts` (new, shared with organizer publishing) serialises the sponsor wallet's transactions so two simultaneous top-ups cannot race for a nonce.
- **The fee (FR-CMP-02):** flat and disclosed, **0 by default**. The page always shows an itemized "What you pay" box. If a fee is configured (`PLATFORM_FEE_MINOR_UNITS` + `PLATFORM_FEE_ADDRESS`), donors get two options, "Cover the fee" and "No thanks", with **neither pre-selected**, and the server refuses a donation that skips the choice. The fee is paid on top, so 100% of the donation reaches the vault. No amount is pre-filled and there is no tip.
- **UI:** a donate panel on the public campaign page (signed-out, own-wallet, switched-off and ready states), a progress display (an amber "Pending: your donation is not complete yet. Step 2 of 4", a green confirmed receipt with an explorer link, a red failure with "Try again"), a receipt/resume page `/donations/[id]`, and "Your donations" on the account page. Failure messages are plain and never leak technical detail (that goes to the server log).
- **Verified live on Polygon Amoy, in a real Chrome:** a brand-new donor whose wallet held 0 POL and 0 mINR signed in, typed 150 rupees and pressed Donate. The page went Pending steps 1, 2, 3, 4 of 4 and showed "confirmed" about 14 s later, and only then. Independent reads through a different RPC: the vault holds exactly 150,000,000; the donor's own wallet sent all three transactions (nonce 3) and the event's donor is the donor's address; the donor's net mINR is 0 (minted 150, deposited 150); the public ledger caught up 10.7 s after confirmation with reconciliation "match".
- **Fee path, real chain:** with a 2-rupee fee configured, the UI rendered two unchecked radio buttons and no pre-filled amount, the API refused a donation with no choice, and a 100-rupee donation covering the fee left the vault at exactly +100, the fee wallet at 2, and the donor at 0. That donation first failed at the fee step because of my own bad test address; the **retry resumed at step 3 of 5**, sent only fee, approve and deposit (donor nonce 4 to 7, nothing minted twice) and confirmed.
- **Bugs found and fixed along the way:** (1) validation crashed with a 500 on a malformed amount because the range check ran `BigInt("abc")` after the format check had already failed (caught by the route tests); (2) a misconfigured mixed-case address was only discovered halfway through a donation, after minting, so **all configured addresses are now checksum-validated when the server reads its config**, with a message naming the setting (live-verified: a bad `PLATFORM_FEE_ADDRESS` now makes the server refuse to run instead of failing mid-donation); (3) my browser-test driver typed before React had hydrated the page, which was a tool race, not an app bug.
- **Tests:** 39 new (170 web total): the whole state machine against a scriptable fake chain (happy path, fee on top, gas skip, idempotency, pending stays pending, unverifiable deposit, an unreachable RPC never fails a sent deposit, revert then retry, failed send then resume, concurrent requests, expired lock, ownership), amount validation, every route including privacy (another donor's donation is a 404) and rate limiting, and config validation. ### 2026-09-19 - Step 8: Indexing core events
- **Approach (SPDD Step 8, "RPC reads"):** the app reads events straight from the chain with viem and stores them; no separate indexer service. `chain_events` is an append-only copy of `CampaignCreated` and `DonationReceived` (id `txHash:logIndex`, so re-reading is idempotent); `indexer_cursors` records how far each stream has been read. Migration `0003_chain_events.sql`.
- **The money rule (SPDD §11.1):** no balance or total is stored anywhere. Totals are computed from `chain_events` on demand with exact BigInt arithmetic, and only `lib/indexer` writes that table. There is no editable "total raised" column to drift.
- **Design:** `lib/indexer/sync.ts` reads the factory first (to discover vaults), then each vault from its creation block. Reads are chunked (default 2,000 blocks); if an RPC refuses a range the chunk halves and retries; a cursor advances only after a chunk's events are stored, so a failure never leaves a gap. Blocks are read only once 2 confirmations deep, so a shallow reorg cannot leave phantom events. It never throws; failures come back as `errors` and the next pass resumes. The core depends only on a `ChainReader` interface (`lib/indexer/types.ts`), so it is tested against an in-memory `FakeChain`; the real viem reader is `lib/chain/reader.ts`.
- **API:** public `GET /api/v1/indexer/status` ("data as of block N" and lag, per SPDD §9.5), public `GET /api/v1/indexer/reconcile` (indexed total vs the vault's own `getBalance()` vs the token's `balanceOf`, at the same block, zero tolerance, SPDD §21 / NFR-17), admin `POST /api/v1/indexer/sync` (force a pass), public `GET /api/v1/campaigns/:id/ledger` (LIVE campaigns only). Reads call `syncIfStale` (10 s window, concurrent callers share one pass), which keeps data inside the lag window without a background worker. The indexer stays off, and says so, unless `FACTORY_ADDRESS` and `INDEXER_START_BLOCK` are set.
- **Verified live on Polygon Amoy (production build, fresh database):** the first pass read about 13,800 blocks from the Factory's deploy block (47,969,967) in 13 s with no errors, using the RPC fallback list (dRPC's free tier times out on 5,000-block log queries; PublicNode and Tenderly served them). It found both campaigns and the 250 mINR donation with the donor and real block timestamp. Reconciliation matched to the unit for both vaults. **Lag test (SPDD acceptance, under 30 s):** a real 10 mINR deposit (block 47,983,818) appeared in the indexer 15.9 s after confirmation, with reconciliation still matching (260,000,000 indexed = tracked = token).
- **A real contract gap found:** vaults emit no event on release (see open items).
- **A wrong test caught, not a wrong indexer:** my first "newly discovered vault" test assumed a `CampaignCreated` event could appear in a block the factory cursor had already passed, which a real chain cannot do. Replaced with the realistic case (a vault created after an earlier pass).
- **Tests:** 29 new (113 web total): idempotency, exact bigint sums, campaign isolation, confirmation depth, lag reporting, unknown lag when the RPC is down, chunk shrinking, no gaps or duplicates after a failure, start-block respect, reconciliation match / one-unit mismatch / unreadable chain, and every route (admin-only sync, drafts hidden, not-configured messages).
- **No CLI watcher was built:** it would have duplicated the sync logic in plain JS (no TypeScript runner is installed). The lazy refresh and the admin sync endpoint cover the need.

- Verify compilation before writing a large contract's full test suite.
- CRLF/LF git warnings on Windows are harmless.
- **Restart `pnpm dev` after adding a migration or changing `apps/web/.env.local`:** the dev server caches its DB connection and env, so a new table or setting is otherwise invisible to it.
- **Public RPCs are flaky:** the official `rpc-amoy.polygon.technology` has been unreachable from this machine; dRPC sometimes returns transient 500s (and its free tier times out on wide `getLogs` ranges). The web app's ordered fallback list absorbs this; your own `cast` commands may need a different `--rpc-url` (PublicNode and Tenderly work).
- **Driving the UI in a real browser (Chrome DevTools):** wait for React hydration before typing, or the input value is overwritten and the button stays disabled.
- **Shell escaping:** backslash sequences (carriage-return plus line-feed) in heredocs, `sed` and Python string literals turned into real line breaks and broke a test file; build such strings with `chr(92)` in Python.
